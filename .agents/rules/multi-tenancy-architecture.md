# Multi-tenancy architecture standards

Use the implemented scoped-port boundary described in [tenant-scoped development](../../docs/architecture/tenant-scoped-development.md). Current Java source and this guidance supersede historical examples using JPA filters, ScopedValue, default tenants, or tenant-selecting application services.

- Ordinary domain/application code must not resolve or rebind execution context, depend on AWS/infrastructure types, select tenants through repository/store arguments, or access global discovery. Permissions and business authorization remain application responsibilities.
- Domain repositories expose tenant-free business operations. Domain creation capabilities hide ownership assignment behind infrastructure adapters and pure factories. Ownership remains explicit immutable record/event data. Adapters resolve current context per operation, fail if absent, and reject foreign-owned writes.
- Both durable and disposable adapters key by tenant plus entity identity. Preserve conditional transitions, atomic idempotency claims, and tenant-qualified reservations. Deliberately shared catalogs expose a separate read-only capability.
- Unified authenticated HTTP ingress uses verified JWT tenant claims. Do not accept tenant selection from an ordinary public header. Internal-token ingress and authenticated AS2 resolution are privileged boundaries with separate deployment trust requirements.
- Trusted workers resolve ownership from durable evidence, bind before lease acquisition, retain scope through processing/release, and restore scope between items. Global discovery belongs only to infrastructure. Durable queue envelopes retain ownership metadata; review producer grants and endpoint/token custody separately.
- `TenantContext` currently uses lexical `ThreadLocal` scopes and restores enclosing context/MDC after success or failure. `TenantExecution` provides trusted run/get/checked-IO adapters and explicit executor capture. The unified application task decorator propagates submitting context. Arbitrary new executors require equivalent propagation; no implicit thread inheritance is assumed.
- Documents and MFT storage ports are scoped. Namespace objects by tenant and authenticate encryption context with tenant/service/resource. Production uses the Hierarchical keyring with one tenant branch beneath the cell-shared root; dedicated physical keys are explicit policy overrides. Local disposable derivation is a test double, never a production security boundary.
- Never use shared plaintext runtime content fallback. Keep classpath reference data separate. Follow [Documents storage migration](../../docs/architecture/documents-storage-migration.md) for retained content and index upgrades; never substitute local reset for deployment migration.
- Tenant-facing DynamoDB schema listing queries the tenant GSI and follows all pages. Administrative scans/backfills use separate migration credentials. Continuation keys must match tenant and expected key shape before data I/O.
- [ArchUnit guardrails](../../tooling/architecture-tests/README.md) enforce these boundaries with an empty violation baseline. Do not add blanket exceptions or regenerate debt. Every new string port input needs exact reviewed business classification.
- Pair structural checks with behavioral contracts for absent context, same IDs in two tenants, foreign writes, read/list/update/delete independence, replay/concurrency, context cleanup, and encryption integrity. Use valid fixture tenant IDs and explicit trusted fixture scope.

Live IAM, JWT issuer settings, internal service credentials, production migration coverage and rollback require deployment evidence; local tests do not establish these facts. Logs/metrics must not contain payloads, secrets, or unbounded sensitive dimensions.
